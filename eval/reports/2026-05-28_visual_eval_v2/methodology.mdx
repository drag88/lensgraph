## What changed since 2026-05-27

The 2026-05-27 run reported `lift = -5.56 pp` and labelled it NON-ACTIONABLE because the 4-channel text RRF passed 18/18 on the visual-required slice — span overlap is the wrong gate when the answer-bearing content lives on the slide and the speaker is talking topically around the same window. This run adds a new metric, `AnswerTermHit@k`, that asks a stricter question of the same retrieval: did the surfaced chunk's TRANSCRIPT TEXT contain the curator-supplied answer-bearing strings (e.g. `NDCG@10`, `is_resumable=True`, `RecoverableExceptions`, jq fragments)? The new metric is reported alongside the existing `VisualChunkTR@k`, not in place of it.

## Important scope statement (what the new metric is, and is not)

`AnswerTermHit@k` is a **text-side diagnostic**. It validates whether the SURFACED TRANSCRIPT CHUNK quotes the answer-bearing strings the curator saw on the slide. **It does not validate that any visual model surfaced the right FRAME, and it does not OCR retrieved frames or call a visual judge.** A real visual answer-grounding metric — one that checks whether the retrieved FRAME actually contains the answer — would need OCR over retrieved frame images or a logged visual judge call per frame; both are out of scope here and remain deferred (see "Next concrete steps" below).

The `visual_evidence` field on a `visual_gold` row records terms the curator confirmed on the gold FRAME. The metric uses those terms only as expected strings the TRANSCRIPT CHUNK should contain. The provenance is visual; the check is textual.

## Actionability rule (verbatim, corrected)

> `AnswerTermHit@k` is a TEXT-SIDE diagnostic and gives an actionable signal iff `n_evaluable ≥ 5` AND the 4-channel text-only baseline fails the metric on ≥1 evaluable example. Lift on this metric (`lift_answer_term_pp`) measures whether the 5-channel RRF surfaces more answer-term-bearing TRANSCRIPT chunks than the 4-channel RRF; it does NOT imply the visual channel is validated against the slide. The legacy `lift_chunk_tr_pp` (span overlap) is reported alongside but is exploratory only and never alone justifies a candidate change. A true visual answer-grounding metric would need OCR over retrieved frames or a visual judge with logged outputs; both are deferred and tracked under "Next concrete steps."

This run satisfies the text-side gate (`n_evaluable = 10`, without-visual fails 10/10). The text-side metric now has signal. Lift on either tier remains `0.0 pp`, so no candidate change is justified.

## Why the text-side baseline fails 10/10

The 4-channel text RRF finds chunks that overlap the gold span via topical relevance, but those chunks' transcript text does not contain the exact answer-bearing strings the curator confirmed on the slide. Two cases pulled from `per_example.jsonl`:

- `visual-required-tengyu-accuracy-plot-axes` — gold span [305, 410] on W_CYk2ogcDI. The text RRF surfaces a topically-relevant chunk that overlaps the gold span (this run also has `visual.retrieve` lands a gold-overlapping chunk standalone — see per_example.jsonl). The chunk's text contains the prose "retrieval quality" loosely but no `NDCG@10`, no `$0.01`, no `$0.10`. The curator's `required_any` terms (NDCG@10 / Retrieval Quality conjoined with $0.01 / $0.10) all miss. Span overlap fires; answer-term does not.
- `visual-required-google-adk-resumability-config-code` — gold span [2010, 2030] on nXafozNIk3c. The text RRF surfaces a chunk where Shubam talks ABOUT resumability ("resume tracks tools that already ran"). The chunk does not contain `is_resumable=True`, `ResumabilityConfig`, or `name='my_resumable_agent'`. Same gold span overlap; no answer term.

`VisualChunkTR@5` cannot distinguish these two cases. `AnswerTermHit@5` does — on the text side.

## Methodology guardrails

### `AnswerTermHit@k` (new, text-side)

Pass for a row iff there exists a top-k chunk that (a) overlaps the gold span on the matching video AND (b) every entry in the row's `visual_evidence` has at least one of its `required_any` terms (normalized per the entry's mode) as a substring of the chunk's **transcript text**. Rows without `visual_evidence` are not evaluable and contribute to neither numerator nor denominator.

Normalization modes:
- `lowercase_collapse_ws` (default) — lowercases and collapses runs of whitespace.
- `exact` — byte-for-byte. Used for code identifiers, kwarg fragments, exact UI strings, version strings.

### `VisualFrameRecall@k`, `VisualChunkTR@k`, `lift_chunk_tr_pp` (unchanged from 2026-05-27)

Same definitions as the prior report.

## Next concrete steps

1. **A real visual answer-grounding metric.** Either OCR retrieved frames and check curator-supplied terms against the OCR output, or call a visual judge per (retrieved frame, expected visual claim) tuple and log its output. Until one of those lands, the visual eval gate is span overlap + a text-side answer-term diagnostic; visual answer support is not measured.
2. **Resolve the 720p → 360p ingester drift** flagged in the band check. Check `ingest/frames.py` defaults and ffmpeg invocation against ADR 005 / phase-1 design intent. Re-ingest at the intended resolution. Re-run this eval. Slide-text legibility may improve.
3. **Stage-1 prefilter ablation** (deferred). Widen `prefilter_k` from 200 to 500 and re-measure standalone visual numbers; the diagnostics report shows 5/10 visual-required rows have the gold frame absent from the top-200 pooled candidates.
4. **Stage-3 MaxSim diagnosis.** Three of the four stage-3 losses ranked the gold chunk at 93/94/111 of ~110 — near-last. That is not "MaxSim ranked it slightly low" — MaxSim is actively demoting slide-text-heavy candidates. Worth a targeted ablation on the MaxSim aggregation.
