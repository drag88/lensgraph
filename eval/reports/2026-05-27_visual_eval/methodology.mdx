## Why two runs

The first run (`visual-eval-3d5384cd6446`) measured 8 visual_gold rows that were curated to have visual answer-bearing content but whose questions still mostly resolved against the transcript. Result: lift = 0 pp, pinned by text saturation. The review feedback called this out and asked for a "visual-required" slice where the answer lives on the slide and **not** verbatim in the transcript. This run adds 10 such rows (3 per-talk subagents curating against the existing frame evidence; transcript-grep verification per row in `eval/curation/visual_gold_review/2026-05-27_required/`). Rows are tagged `["visual-required", ...]` in `visual_gold.jsonl` so the eval can be sliced by tag without a runner change.

The expected outcome was "text-only misses at least one" → lift becomes measurable in the positive direction. **What we got: text-only catches all 10, and adding the visual channel actually displaces the right chunk on one example.** Concretely: `visual-required-google-adk-resumability-config-code` (gold span [2010, 2030] on `nXafozNIk3c`) — text RRF puts the gold chunk in its top 5, but the 5-channel RRF (with visual added) does not. ColQwen's visual contribution outranks the text-found chunk on this query.

This is not "ColQwen is broken" — n=10 is small, and one regression on a tightly-specific code question is within noise. But it is a useful exploratory observation: in the regime where text retrieval already saturates, adding a fifth channel via vanilla RRF is **at best neutral** and can be slightly negative.

## Why the acceptance gate failed

The acceptance criteria asked for examples where text-only RRF misses. We curated 10 visual-required questions whose answers are demonstrably NOT in the transcript verbatim (per-row transcript-grep evidence in `eval/curation/visual_gold_review/2026-05-27_required/*/notes.md`). All 10 still pass under text-only RRF because of a **measurement-model mismatch**:

- The TR@5 / open-interval overlap metric measures "did the retriever surface a chunk that overlaps the gold time window?", not "does the surfaced chunk contain the answer-bearing text?".
- Even when the answer-bearing CONTENT is visual (on the slide), the speaker is TALKING about that topic during that span. The chunk's transcript text is therefore topically dense around the question's keywords. Text channels (dense + sparse + multivec + BM25) surface that chunk on topicality alone.
- The gold span overlap test then passes, even though the chunk's text would not, on its own, answer the visual-required question.

**Implication for the visual eval design.** To make lift actionable on this kind of corpus, the next iteration needs a metric that goes beyond span coverage. Two candidates worth scoping next:

1. **Answer-grounded eval.** Add a faithfulness judge that scores whether the retrieved chunk's TEXT actually contains the answer. For visual-required examples, the judge should fail the text-only path even when TR@5 passes. Lift then measures "did adding visual rescue the cases where text retrieval is topical-but-not-answer-bearing?"
2. **Visual-only baseline.** Run `visual.retrieve` standalone on the visual-required slice and report its standalone numbers — already done above (1/10 chunk_tr@5, 1/10 frame_recall@5), but pair it with a transcript-anchored visual-required corpus where the visible content has zero topical overlap with the gold-span transcript (very hard to engineer naturally on conference talks).

Both are bakeoff #2-or-later concerns. For now, **lift remains non-actionable on this corpus** and no model swap, no candidate change, no production decision is justified by these numbers.

## Methodology guardrails (unchanged)

### VisualFrameRecall@k
Pass if any top-k frame from `retrieve.visual.retrieve_frames` satisfies `frame.video_id == gold.video_id AND gold.start_sec - tolerance_sec <= frame.frame_sec <= gold.end_sec + tolerance_sec`. Default `tolerance_sec = FRAME_SAMPLE_EVERY_SEC = 10.0`.

### VisualChunkTR@k
Pass if any top-k chunk from `retrieve.visual.retrieve` overlaps the gold span (open-interval).

### VisualLift@k
Per-example pass on `rrf({bm25, dense, sparse, multivec, visual}, top_k=5)` vs `rrf({bm25, dense, sparse, multivec}, top_k=5)`, reported as `(with_rate - without_rate) * 100` in percentage points. **Actionable iff** the without-visual baseline misses ≥1 example. Today: it does not, so lift is non-actionable on this corpus.
