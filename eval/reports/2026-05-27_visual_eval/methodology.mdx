## What this gate is — and what it is NOT

Bakeoff #1 (2026-05-27, `eval/reports/2026-05-27_embeddings_bakeoff/`) locked **text embeddings only** (`bge-m3-all-channels`, vector-best TR@5 = 1.00). Its candidate set (`candidates.text_embeddings`) and its minimum (`timestamp_recall_at_5_vector_only_min: 0.75`) cover the three BGE-M3 text channels — `dense`, `sparse`, `multivec` — and report RRF over those plus BM25. **Visual retrieval is the 5th channel in the production loop (`generate/nodes/retrieve.py`) and is NOT covered by that minimum.** Quality of the visual channel is the responsibility of THIS gate, on its own corpus, with its own metrics.

This report is a **stub** because one prerequisite is still not in place:

1. **Verified visual gold examples.** Done. `visual_gold.jsonl` now has 8 verified single-clip examples, curated from all 10 `dev_gold.jsonl` single-clip rows. The curation accepted rows only when the transcript span and visible slide/screen/diagram evidence were answer-bearing in the same window. Two transcript-only rows were rejected: `tengyu-two-reasons-to-chunk` and `sally-staying-on-task-attention`. Evidence lives under `eval/curation/visual_gold_review/2026-05-27/`.
2. **Ingested MP4 frames + ColQwen patches.** Still missing. `frames` and `frame_patches` are both empty in the live DB (no `.mp4` files have been staged). `retrieve.visual.retrieve_frames()` and `retrieve.visual.retrieve()` already handle the empty-substrate case by returning `[]`, but a recall metric over `[]` is degenerate.

Until both prerequisites are satisfied, the runner skips with a clear message; the test asserts the skip text so the gate cannot silently rot.

## Metrics

The eval implements three primitives in `eval/runners/measure_visual.py`:

### VisualFrameRecall@k
Pass if any of the top-k frames from `retrieve.visual.retrieve_frames` satisfies:

```
frame.video_id == gold.video_id
AND gold.start_sec - tolerance_sec <= frame.frame_sec <= gold.end_sec + tolerance_sec
```

Default `tolerance_sec = FRAME_SAMPLE_EVERY_SEC = 10.0` — the cadence `ingest/frames.py` uses when sampling PNGs from MP4s. The tolerance protects a gold span that lands between two sampled frames (e.g., gold `[174, 184]` with frames at 170, 180); it is documented explicitly so future tightening goes through review.

### VisualChunkTR@k
Pass if any of the top-k chunks from `retrieve.visual.retrieve` satisfies open-interval overlap with the gold span — exactly the convention bakeoff #1 used for text TR@5:

```
chunk.video_id == gold.video_id
AND chunk.start_sec < gold.end_sec
AND chunk.end_sec   > gold.start_sec
```

This is the chunk-level form of recall, capturing the full 3-stage ColQwen pipeline (pooled prefilter → frame-to-chunk map → MaxSim refine over frame patches).

### VisualLift@k (optional; on by default)
For each visual gold example, compare:

```
with_visual    = rrf({bm25, dense, sparse, multivec, visual}, top_k=5)
without_visual = rrf({bm25, dense, sparse, multivec},          top_k=5)

lift_pp        = (pass_rate(with_visual) - pass_rate(without_visual)) * 100
```

`without_visual` is identical to the `rrf_4ch` channel measured in bakeoff #1. Lift answers: "does adding the visual channel help on examples where visual signal is hypothesized to matter?" This is what justifies keeping ColQwen in the production loop at all.

Lift is small-sample noisy by construction — on a 5-example visual gold a single flip is 20pp. Treat single-digit lift values as inside the noise; treat large negative lift on slide-required modality as a real signal to investigate before claiming visual retrieval is pulling its weight.

## Outputs (when the gate runs)

Same eval_runs + eval_results contract as bakeoff #1 (phase-2 hard rule):

- One `eval_runs` row with `code_path = 'visual_eval'`, `embedding_model_id = 'colqwen2.5'`, `summary` carrying `visual_frame_recall_at_k`, `visual_chunk_tr_at_k`, optional `visual_lift`, `per_example` (pass booleans), and the candidate yaml SHA.
- One `eval_results` row per visual gold example, with `system_output` carrying the gold span + the top-k frames and chunks the runner actually retrieved, and `metrics` carrying the pass booleans (and lift per-example when computed).
- Writes are wrapped in a single transaction; a mid-loop failure rolls back. (Same atomicity contract as the bakeoff #1 review-fix #2 patch.)

**No winner is locked.** ColQwen2.5 is the only candidate; there is no ADR 004 selection to encode. If a second visual candidate is added in the future, the gate becomes a selection bakeoff (and gets its own MDX at that point).

## Skip semantics

`scripts/run_visual_eval.py` exits **0** with a clear `SKIPPED: ...` line in either of:

```
SKIPPED: visual_gold.jsonl has 0 single_clip examples. ...
SKIPPED: visual substrate not ingested for visual_gold video_id(s):
         <video_id>(frames=0,patches=0), ...
```

The first skip remains for future empty-corpus regressions. In the current repo, the expected skip is the per-video substrate message listing the `visual_gold.jsonl` video IDs that lack frame embeddings and patches. The slow integration test (`eval/tests/test_run_visual_eval.py`) asserts the right skip text is emitted and that NO `eval_runs` row leaks during a skip. The fast unit tests (`eval/tests/test_measure_visual.py`) cover the metric primitives with synthetic `FrameResult` / `ChannelResult` / `FusedResult` inputs — those run under `make test` in ~1s.

## What it takes to unblock the gate

1. **Visual gold is already curated.** The 8 accepted examples cover all three dev talks. Keep the `eval/curation/visual_gold_review/2026-05-27/` notes with the corpus rows so future reviewers can inspect the frame evidence. Do not promote rejected transcript-only rows unless a new narrower visual question is created with fresh evidence.

2. **Ingest MP4 frames + ColQwen patches.** `ingest/frames.py` and the ColQwen patch worker need to run against the source videos (`videos/<video_id>.mp4`, gitignored). Once `frames.pooled_embedding` and `frame_patches` are populated, the substrate check in `run_visual_eval.py` flips from SKIP to RUN automatically.

3. **Run the gate.** `uv run python -m eval.runners.run_visual_eval` produces the `eval_runs` row + per-example `eval_results` and stdout-reports the metrics. The slow integration test starts asserting against real numbers instead of just the skip path. (A back-compat shim at `scripts/run_visual_eval.py` still works but the canonical entry point is under `eval/runners/` because this module defines an eval run.)

## What's deliberately out of scope

- **No second visual candidate yet.** Adding `gemini-embedding-2-singlevec` to a real bakeoff is a possible future amendment; today it lives in the YAML only as a baseline reference for the writeup.
- **No bakeoff #2 (generator + judge) interaction.** This gate measures retrieval. Faithfulness on visual-required examples is a downstream concern for bakeoff #2's generator + judge.
- **No `test_gold` consumption.** As with bakeoff #1, only `dev_gold` (here: `visual_gold.jsonl`) informs anything. The locked text `test_gold.jsonl` is untouched.
