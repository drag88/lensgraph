## What this report establishes

The v2 metric `AnswerTermHit@k` was a text-side diagnostic — it checked whether the retrieved TRANSCRIPT chunk's text contained the curator's slide terms. The reviewer correctly flagged that this does not validate the visual channel: ColQwen could surface no frame at all and the metric could still pass via transcript topical overlap.

This run adds `VisualAnswerGrounding@k` — a **frame-side** metric that:
1. Calls `retrieve.visual.retrieve_frames(conn, query, top_k=5)` to get the top-k frames the visual channel actually surfaced.
2. For each frame, OCRs the on-disk PNG via `pytesseract` (Tesseract 5.x, PSM 3, eng) and concatenates the detected text.
3. Passes the row iff some top-k frame both (a) sits within `gold.video_id` and within `[gold.start_sec - 10s, gold.end_sec + 10s]` AND (b) its OCR text contains the curator's `visual_evidence.required_any` terms (same normalization rules as the text-side metric).

If ColQwen retrieves an answer-bearing frame, this metric fires. If not, it fails. There is no transcript-side path that can falsely satisfy it.

## Conclusion — defensible failure with named next fix

**ColQwen2.5, ingested at 360p source (h264, ~88 kbps), does not surface answer-bearing frames for slide-text-heavy queries on this corpus.** All 10 visual-required rows fail at the **window gate** — the visual channel doesn't even bring the right frame into the top-5. OCR is operationally correct (tested via fast tests with mocked `ocr_fn`; pytesseract + Tesseract 5.x are installed and importable), but irrelevant: the upstream retrieval doesn't surface a frame to OCR.

This matches the diagnostic report at `eval/reports/2026-05-28_visual_diagnostics/report.md` from the prior session: 5/10 lose at stage 1 (pooled HNSW prefilter — gold frame absent from top-200), 4/10 lose at stage 3 (MaxSim demotion to ~last). The new frame-side metric confirms the *consequence* of those retrieval losses: zero answer grounding on any visual-required row.

## OCR audit payload — REQUIRED before relying on any positive result

The current runner writes only the boolean `visual_answer_grounding_at_k` per row in `eval_results.metrics`. That is fine while the result is 0/10 and the failure is upstream of OCR, but it is **not** enough to defend a future positive. A `vag = true` row with only a boolean cannot be audited — there is no record of which in-window frame was OCR'd, what text was returned, or which `required_any` term matched.

Before the next session interprets any positive `VisualAnswerGrounding` result, the runner must record a structured audit payload per row. Minimum fields (also documented in `integrity_check.md` §B):

- `passed: bool`
- `evaluated_frame_ids: [int]` — the in-window top-k frame IDs OCR was run against
- `evaluated_image_paths: [str]`
- `ocr_excerpts: {frame_id: str}` — first ~500 chars of OCR per evaluated frame
- `matched_term: str | null`
- `failure_reason: "no_in_window_frame" | "ocr_no_terms_matched" | "row_not_evaluable" | null`

A `TODO(v4)` marker is in `eval/runners/measure_visual.py` and `eval/runners/run_visual_eval.py` flagging the same gap. The 0/10 result in this report does not depend on the payload; any positive result from a future run does.
