## Setup

Both strategies' chunks coexist in the `chunks` table (natural key includes
`chunking_strategy`). Retrieval is strategy-filtered — every text channel
(`dense`, `sparse`, `multivec`, `bm25`) takes `chunking_strategy`
(default `fixed_window`, so production is unaffected). Same 10 single_clip
dev_gold queries, same channels, top-5. `transcript_segment` was chunked +
embedded via the strategy-aware `chunk_handler` (`strategy` payload key) +
`ingest_embed_text` drain.

## The load-bearing caveat — why this is not "transcript_segment wins"

**TR@5 structurally favors larger chunks.** The metric asks "does the gold span
fall inside any top-5 chunk?" — a 90s chunk is far more likely to contain a span
than a 30s one, regardless of boundary quality. So transcript_segment's equal
recall at 2.6× the chunk size is **not** evidence it retrieves better; partly it
just has bigger nets.

What this run does NOT measure (and what a real selection needs):
- **`GoldSpanContained@k` / `IoU@1`** — does the chunk *tightly* contain the
  span, or is it bloated? This is where 90–156s chunks should lose. Not run here.
- **Citation accuracy / answer faithfulness** — a 150s chunk makes a precise
  timestamped citation harder. The generation tier, not measured here.
- **Boundary edge/standalone** — the original motivation. Needs the
  cold-kappa-validated boundary judge first.

## Decision

**No winner. Provisional.** Recorded honestly: transcript_segment preserves
retrieval recall while producing cleaner but much coarser chunks. Whether the
cleaner boundaries are worth the coarser granularity is undecided until
`GoldSpanContained`/`IoU` + citation accuracy + a validated boundary kappa are
run. No `lock_bakeoff_winner`; no ADR amendment.
